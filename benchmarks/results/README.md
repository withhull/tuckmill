# Baseline results

One directory per run, written by `scripts/bench-baseline.sh <model.gguf>`
under the tier of the machine that ran it. Every number is
**locally-calibrated** evidence for that machine, not a claim; claims live
in `docs/claims.md` only after the controlled protocol in
`../README.md` is met.

| Tier (unified memory) | Directory | State |
| --- | --- | --- |
| 8 GB | `8gb/` | recorded on MacBook Air M3 8 GB (see dated runs) |
| 16–24 GB | `16-24gb/` | ⛔ pending: no machine available; run the script unchanged |
| 36–48 GB | `36-48gb/` | ⛔ pending: no machine available; run the script unchanged |
| 64 GB+ | `64gb-plus/` | ⛔ pending: no machine available; run the script unchanged |

## What a run contains

- `environment.json` — chip, memory, macOS, power source, tuckmill commit
  (and whether the tree was dirty), pinned llama.cpp revision, artifact
  size and SHA-256, workload shape.
- `runs.tsv` — every invocation in execution order (ABBA), with reclaimable
  memory before it, swap growth during it, and its status (`ok`, `failed`,
  `discarded-swap`). Discarded and failed runs stay listed; they never
  enter a median.
- `records/*.json` — the unmodified `tuckmill bench` records (schema v4)
  for each invocation, plus each invocation's stderr.
- `llama-bench.json` — the pinned `llama-bench` tool on the same file (its
  own prompt tokens: a vendor-tool row, not identity-matched).
- `mlx.json` — whether mlx-lm can load the identical artifact; an MLX
  conversion is a different artifact and is never compared.
- `summary.md` — generated by `scripts/bench_summary.py`; use
  [TEMPLATE.md](TEMPLATE.md) to read it.

## Reproduce

```bash
scripts/fetch-llama.sh
scripts/bench-baseline.sh path/to/model.gguf
```

Knobs: `ROUNDS`, `INPUT`, `OUTPUT`, `REPS`, `CONTEXT`,
`MIN_RECLAIMABLE_MIB`, `SWAP_DISCARD_MIB` (see the script header). Close
other heavy apps first; the script refuses to start a model process below
the reclaimable-memory floor and runs one model process at a time.
